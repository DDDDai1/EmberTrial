# 项目报错与问题提交方式

原则：**可复制的错误发文字；连线 / 布局问题发截图；动作 / 时序问题发短视频。**三种方式可组合，不需要把所有材料一次准备齐全。我能读取本地工程时，给准确路径和发生时间通常就能开始排查。

## 1. 按问题选择材料

| 问题 | 优先材料 | 补充内容 |
|---|---|---|
| C++ 编译、UHT、链接 | Visual Studio“输出 → 生成”的原始文字 | 第一个实际 error 前后约 20–40 行、最后的失败摘要；文件名 / 行号 |
| 工程创建失败 | 弹窗完整文字、实际工程目录 | 弹窗截图可补充；不要只告诉我“创建不了” |
| Blueprint 编译 / Accessed None | Compiler Results / Message Log 的错误文字 + 相关节点截图 | 包含执行线、关键数据线、节点名称、蓝图资源路径与变量类型 |
| UI 布局、颜色、遮挡、焦点 | 游戏运行截图 + 预期描述 | 分辨率、窗口模式、使用键鼠还是手柄；必要时补 Hierarchy / Details |
| 动画、碰撞、状态切换、偶发输入 | 10–30 秒短视频或简短逐步复现 | 从正常状态录到异常；说明按了哪些键、30 / 60 等帧率条件 |
| 崩溃 | 崩溃提示文字 / 调用栈、崩溃时间、日志与 Crashes 路径 | 最近操作；是否每次必现；不要清空 Saved 后才报告 |
| Cook / 打包失败 | Output Log / AutomationTool 原始日志 | 从首个具体错误开始；末尾“Unknown Error / ExitCode”通常只是摘要 |
| 卡顿 / 性能 | 触发路线、当时场景、帧率变化 | 设备、分辨率、画质；我再决定是否采集 Insights，不要求你先分析 Trace |

Visual Studio 的“错误列表 / Error List”可能包含 IntelliSense 的派生问题。构建错误以“输出 / Output → 生成 / Build”记录为主，截图错误数量不能代替原始日志。

## 2. 最小模板

可以直接复制，无法确定的字段写“不确定”，不用为了填表耽误排查：

```text
任务 / 步骤：例如 M0-01B，关闭编辑器后在 VS Build
发生时间：例如今天 20:15 左右
我刚做了什么：
预期发生什么：
实际发生什么：
是否每次复现：每次 / 偶发 / 只出现一次
最近改动：文件、蓝图或设置；不确定可写不确定
工程 / 资源 / 日志路径：
编辑器是否打开、改动是否已保存：
错误原文 / 附件：
```

实在难描述时一句话也可以：“角色重生后血条不动了，刚保存完；请你直接检查。”有截图或视频就附上，没有也先报告。我会先读取工程与日志，再只追问仍缺失的信息。

## 3. 当前工程的日志位置

以下工程相关路径在实际创建或运行后才可能出现：

- 编辑器日志：`E:\UE_Project\Demo\EmberTrial\Saved\Logs\EmberTrial.log`。
- UBT 日志：通常为 `C:\Users\D1334\AppData\Local\UnrealBuildTool\Log.txt`，以本次构建输出的日志路径为准。
- 工程崩溃资料：`E:\UE_Project\Demo\EmberTrial\Saved\Crashes`。
- AutomationTool 日志：通常在 `C:\Users\D1334\AppData\Roaming\Unreal Engine\AutomationTool\Logs` 下，以打包输出为准。
- 已打包游戏日志可能位于用户本地应用数据目录，不一定仍在工程的 Saved 目录；届时按该构建实际路径查找。

日志可能被后续运行覆盖。出现问题后，先告诉我时间与路径；若需要保存现场，可以把相关日志复制到 `E:\UE_Project\Demo\Docs\Reports` 下按日期命名。这个目录仅在实际需要时创建；大型 dump / Trace 不放进普通 Git 提交。

## 4. 截图与视频怎么拍更有用

- 蓝图截图优先一张局部清晰图，包含相关执行链与引脚；必要时再补一张整段流程。不要只拍被裁掉名称的红色节点。
- 说明蓝图资产完整路径，例如 `/Game/EmberTrial/Blueprints/BP_...`。节点多时，也可选中相关节点 Ctrl+C，另发复制出的节点文本；不必手工抄写。
- UI 同时说明“哪里不对”和“你希望是什么样”，尽量包含分辨率和操作前后状态。
- 视频不用剪辑包装，能看到触发过程即可。无法录制时写按键顺序和复现频率。
- 不需要发账号、密码、令牌等无关内容；若日志含有这些信息，只删敏感值，不删错误上下文。

## 5. 我接手后的处理方式

1. 确认问题现场、代码 / 资源状态，读取原始日志，不要求你先猜原因。
2. 定位最早的有效错误和相关改动，避免把后续连锁错误当成多个独立问题。
3. 在已授权工程范围内修复；复杂问题不反复要求你按截图代改大量代码。
4. 若必须你操作编辑器，明确写出“操作路径、动作、预期结果”；需要关闭编辑器时解释原因。
5. 报告根因、改动、实际验证结果和剩余手工验收。修复后把值得复盘的案例写入 DebugDiary。

报错后不必盲目删除 `Binaries` / `Intermediate` / `Saved`、重装 UE、切换版本或关闭安全功能。这些操作若确有必要，会先根据证据说明用途与保留现场的方法。
