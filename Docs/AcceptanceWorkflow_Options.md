# EmberTrial 验收流程调整：方案比较与选择记录

方案选择日期2026-10-05，维护更新2026-10-28。适用工程：UE 5.5.4 / EmberTrial，个人开发、每周约30小时、键鼠交付。**用户已选择方案B并持续执行。**当前01 / 02A已验收、B战斗属性 / 效果待手动；实时状态见[Progress](Progress.md)。本页保留方案比较、最终选择与可复用的执行规则。

## 1. 当前结论与需要解决的问题

**建议选择方案B：按改动风险分层验收，复用测试入口，并逐步自动化稳定且反复执行的规则。**先减少不必要的重复，再按实际需求建设小型测试工具，不把开发重心转移到大型测试平台上。

选择方案时，M1-03B3手动约70分钟，包含配置、接线、测试和清理；未分别计时，不能全部算验收开销。当时Waiting样例走了依赖缺失而非预期100/60配置拒绝路径，后来用原生类新建样例局部补查并关闭；见[B3报告](Reports/M1_03B3_Verification.md)。已通过部分保留，没有重建全套测试。

你的问题成立。此前流程把学习蓝图、首次验证系统边界和重复回归混在一起：每批在正式Controller搭临时按键 / 函数 / 引用，验证后删除，下批再搭相似入口。B3的五函数 / 五变量尤其增加了操作成本。后续功能变多，如果继续逐模块重建全部旧功能的测试入口，工时会持续增加。

B2验证View生命周期、B3验证真正不同的数据源，两者有不同目的；已经验证的数据流基础仍有价值。但这些边界在实现未变时不应每加一个技能都完整重做。后续要区分：

- **新功能验收：**确认新功能及直接相邻系统能工作。
- **旧功能回归：**按本次修改影响范围选择用例。
- **工具建设：**让重复操作可以复用；它有独立工时预算，不能无限扩张。

选择当次只记录方案、不进入新章节；此后按用户授权继续开发。后续形成了原生开发命令、配置 / 资产校验与自动化；第8节记录当前入口及其边界，不再逐阶段复制流水。

## 2. 估时口径

下列时间是按当前工程复杂度、用户已有Gameplay / UI经验作出的**规划估计**，不是测量结果或行业统计。主要计算人的设计、配置、执行、分析时间；Build / Cook / 引擎启动等等待另计。新功能本身的开发时间不包括在内。

“普通批次”指类似增加一个稳定能力、一个UI展示或少量参数；修改ASC归属、Pawn生命周期、公共输入、暂停或UI绑定属于高风险批次，不能套用普通批次的上限。首次接入新系统仍需充分验证，后续改动才享受复用收益。

| 方案 | 初始投入 | 普通批次手动检查 | 后续新增 / 维护测试的投入 | 遗漏风险与实际项目适用性 |
| --- | --- | --- | --- | --- |
| A：精简手动验收 | 0.5–1.5小时，整理清单与影响范围 | 5–15分钟 | 简单改动很少；缺入口的复杂场景仍可能另花15–60分钟搭临时逻辑 | 风险中等；小团队 / 原型阶段适用，长期仅靠手动容易遗漏 |
| B：分层验收 + 复用测试入口，推荐 | 4–8小时，分批建设当前实际需要的工具 | 5–15分钟 | 已有入口通常无需新接线；普通增量约0–20分钟，复杂新场景可能30–60分钟 | 风险低至中等；适合当前个人Demo，也适合有持续迭代需求的团队 |
| C：自动化优先 | 16–30小时，建立当前属性 / UI核心链路的自动化基线 | 3–8分钟视觉 / 输入检查 | 稳定接口新增断言约30–120分钟；异步 / 输入 / 世界场景可能更久 | 逻辑回归风险较低；适合稳定且长期维护的系统，早期频繁重构成本高 |

风险等级表示相对遗漏可能性，不是缺陷概率。没有任何方案能保证零遗漏。真实项目是否采用还受人员、QA、交付周期和平台影响；这里不虚构采用率，也不推断游戏科学内部流程。

## 3. 方案A：精简手动验收

**做法：**保留明确的验收标准，减少执行范围和重复次数，暂不建设统一测试台。

每批只做“新功能 + 被修改的相邻功能 + 一次简短主流程”。已经通过且实现未变的三轮往返、十次重建、三种帧率等专项，不再作为每批默认要求。修复Bug只验证原复现路径和相关边界，不重做无关模块。

例如只调整血条布局，检查布局、数值变化、菜单覆盖即可；无需重新搭换身体、销毁旧ASC、非法配置的完整矩阵。若修改Presenter解绑，则对应旧源 / 旧View隔离仍必须检查。

**时间：**立即可用；高风险批次预计15–40分钟检查，若没有可用入口还要增加准备时间。一个阶段结束安排30–60分钟集中主流程检查，打包专项另计。

**遗漏风险：**人工可能漏掉间接依赖；较复杂场景仍依赖临时蓝图，操作和恢复容易出错。基础组件被改动时需要扩大检查范围，不能只看新功能成功路径。

**实际项目适用性：**短期原型、探索玩法、小团队可以采用。作为成熟项目唯一长期保障不够充分；通常还会配合QA、自动化或固定测试环境。这是适用性判断，不是对行业采用比例的统计。

**对我们：**最快减少流程负担，但没有彻底解决“反复设计测试入口”的核心问题。

## 4. 方案B：分层验收 + 复用测试入口

### 4.1 修改决定测试范围

日常优先完成新功能及直接依赖。保留固定、短小的可玩主流程；专项用例只在相关实现变化、出现Bug或阶段收尾时执行。

| 本次修改 | 需要检查 | 不默认重复 |
| --- | --- | --- |
| 字体 / 颜色 / 血条布局 | 目标画面、一次数据刷新、涉及的焦点 / 遮挡 | 属性上下限、不同身体、十次HUD重建 |
| 扣血 / 治疗 / 最大值规则 | 合法值、边界、真实Effect、HUD响应 | 无关动画、全部Pawn替换矩阵 |
| Presenter / Bootstrap / 解绑逻辑 | 快照、重复订阅、旧源隔离、销毁 / 重建、结束清理 | 无关能力的全部参数组合 |
| Pawn / ASC所有权或GameplayReady | 不同身体、Ready / Waiting / Unsupported / NoPawn、旧源隔离、结束清理 | 无关UI排版与全部攻击视觉细节 |
| 公共输入 / 暂停 / 动作门控 | 相关动作、按住 / 松开、暂停恢复与无补执行 | 全部生命最大值边界 |
| 闪避位移 / CharacterMovement | 墙 / 坡、打断、暂停、帧步长相关测试 | 未受影响的HUD换源矩阵 |
| 打包配置 / 资源引用 / 模块边界 | 正常构建、实际Cook与独立包加载、关键资源和输入 | 用PIE成功替代包内检查 |

这张表用于选择用例，不能把“没有默认重复”记成“本次已通过”。跳过项记录为“已验收基线未受本次改动影响，沿用”，避免虚假验收。

### 4.2 小型测试环境只建一次

原方案曾提出独立测试地图及专用GameMode / Controller；目前没有建设通用测试台，也不把4–8小时预算当成必须先投入的工时。优先复用正式流程、已有测试资产、受限PIE命令与原生自动化；仅当反复需要而现有入口不足时再建设专用场景。

若建设第一版，只覆盖确实重复的身体修改 / 更换、销毁、HUD重建和快照查询；公共准备与清理集中复用。不提前造出覆盖未来全部系统的工具，也不把每批新建再删除Controller临时函数作为默认流程。

测试入口必须调用真实Gameplay / Presenter / Bootstrap接口，不直接修改HUD显示、不广播伪造Ready，也不复制一套生产规则。每轮独立创建对象、重置环境并释放订阅，避免用上一轮残留状态得出假通过。

Tests目录名不自动隔离打包。第28批只读引用审计确认训练目标和Damage25仍被正式资源引用，禁止直接整目录NeverCook或删除。候选测试资源须逐项查引用 / 加载方式，迁移或排除后再实际Cook核对；包级图不能证明蓝图执行线。现有PIE资源修改命令有Editor / PIE限制，其他兼容入口保留原因见[架构](Architecture.md)。

### 4.3 自动化按收益增加

保留Lifecycle / DodgeMovement作为Practice兼容层回归；正式GAS闪避、连段和治疗已有各自专项，不能用M0组件测试证明正式能力正确。改到动作生命周期或位移时运行相关测试，不因改一个UI颜色就强制跑完整动作专项。

优先自动化稳定且有明确结果的规则：属性夹取、成本 / 冷却、状态迁移、委托解绑与旧源隔离。动画观感、UI焦点、镜头和可玩体验保留短手动检查。测试新行为或真实Bug，避免只复述实现代码。

凡是同一套临时接线第二次出现，先评估复用；准备成本超过单批预期时，先简化验证入口，不继续堆长蓝图。自动化的编写 / 维护时间单独列出，收益不足时允许暂缓。

**时间与建设边界：**总计4–8小时分批投入，约每周30小时的13%–27%；这是现有属性 / UI场景的最小工具范围，后续新系统增量另计。先用0.5–1.5小时整理现有检查清单，随后只在重复需求出现时投入工具；每批新增工具原则上控制在1–2小时内。工具预算超出8小时先回顾收益和范围，再决定是否扩展。

**运行频率：**日常普通批次5–15分钟，高风险批次15–30分钟并运行相关专项；阶段收尾30–60分钟，汇总已有证据，只补缺口，不重建B3测试逻辑。实际失败会额外增加排查时间。

**遗漏风险：**影响范围判断可能漏掉间接依赖，工具本身也可能有Bug。应保留阶段主流程、真实打包和固定的数据源边界专项，并让测试台显示对象身份 / 实际返回值。日志审查只能补充证据，不能代替画面和输入检查。

**实际项目适用性：**对个人Demo和持续迭代团队都较合适。UE原生支持C++自动测试和Blueprint关卡功能测试，因此这条路线可以逐步扩展。[Epic Automation Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-test-framework-in-unreal-engine)、[Epic Functional Testing](https://dev.epicgames.com/documentation/unreal-engine/functional-testing-in-unreal-engine?lang=en-US)。是否值得自动化每个场景，是我们的工程判断。

**对我们：**解决反复接临时逻辑的问题，同时保留关键生命周期证据，最符合“新功能优先、工程能力可展示”的目标。

## 5. 方案C：自动化优先

**做法：**先为现有核心链路建立可重复运行的测试，再把后续稳定的新功能验收尽量写成自动测试；人工主要检查画面、输入和完整可玩体验。

C++层使用UE Automation测试属性与状态规则；涉及World / PlayerController / LocalPlayer / Widget的真实集成使用专用测试场景与合适的功能测试。统一准备、断言、超时、清理、输出和失败报告。一次通过日志不能冒充全部自动化断言。

**时间：**16–30小时仅估算当前核心逻辑 / 属性与UI生命周期的本地自动化基线，约0.5–1个投入周。它不包括把全部动画 / 鼠标焦点 / 包体流程自动化，也不包括完整云CI。后续普通稳定功能新增断言约30–120分钟；新异步场景可能更久。运行本身会较短，但引擎启动和构建等待仍存在，不能承诺总耗时只有几秒。

CI可以后续再接；本地脚本与Session Frontend已能执行测试，无需为了验收先安装GitHub插件。若未来要自动启动并检查打包后的游戏，可评估Gauntlet；它负责运行会话与结果验证，不负责创建构建，仍需要实际包。[Epic Gauntlet Overview](https://dev.epicgames.com/documentation/unreal-engine/gauntlet-automation-framework-overview-in-unreal-engine?lang=en-US)。

**遗漏风险：**可重复的数值 / 状态用例覆盖更稳定，但断言写错、模拟对象过简、绕过真实蓝图或忽略UI输入都会造成假通过。NullRHI等无画面运行不能证明动画、鼠标焦点或视觉正常；时间相关测试不能靠随意Delay制造成功。

**实际项目适用性：**稳定且长期维护、经常集成、有人维护测试的项目更适合。玩法快速变化的原型如果每次重构都重写整套端到端测试，可能拖慢开发。这是对条件的判断，不意味着个人开发不能使用自动化。

**对我们：**能形成较强工具 / 自动化展示材料，但此时一次投入较大；用户仍默认手动编写C++，学习与录入工时不能省略。更适合作为方案B后续的增量方向，而非当前立即全面切换。

## 6. 如何判断省下了时间

先记录接下来3个开发批次的四项时间：功能实现、测试入口准备、检查执行、问题排查；构建 / 启动等待另列。目标是降低“入口准备 + 重复执行”，不能通过取消必要新功能验证制造节省。

可用粗略回本公式：

`预计回本批次数 = 一次性工具投入分钟 ÷ 每批减少的准备与执行分钟`

例如工具投入6小时，每批实际节省20分钟，则约18批回本；若只节省10分钟则约36批。这只是示例，未计维护成本，不能宣称本Demo一定达到这个收益。若某个专项后面几乎不会再动，保存一次性证据通常比全面自动化更划算。

因此不建议“先自动化所有旧功能再做新功能”，也不建议“平时完全不检查、等投递前一起测”。前者会继续让测试建设挤占功能开发；后者使故障累积、定位和返工更困难。真正的效率来自减少重复准备、控制范围和复用。

## 7. 选定后我们的合作方式

我在每节开头给出：本批新增行为、受影响系统、沿用基线、必须执行的最小用例及预计检查时间。必要蓝图依然逐节点说明，不能以简化流程为由省略关键Target、数据引脚或执行出口；已经有的测试工具直接使用入口与配置。

普通批次反馈可以缩为：新功能结果、相关检查结果、失败项、完成时间、实际用时和保存状态。日志由我读取；只有连线不明确、视觉异常或时序问题才需要截图 / 短视频。不再要求每批复制全部旧功能验收表。

失败项明确列入待修，不以“下次再说”标为完成。阶段 / 打包 / 投递前仍检查完整作品，但复用固定工具与清单、已有自动测试和历史证据，不要求重新设计验收功能。没有新修改或风险，不扩大或反复执行同样检查。

方案选择本身不授权接管代码或编辑器。一般功能开发仍先给操作文档、由用户实践；本轮清理已有用户明确授权，助手直接修改并保留快照 / 验证。用户已授权验收无问题时保存报告并直接下发下一章；当前按约定验收A后同轮进入B，普通C++仍手动实现。
